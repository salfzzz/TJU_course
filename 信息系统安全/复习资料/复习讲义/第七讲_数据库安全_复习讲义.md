# 第七讲：数据库安全——复习讲义

> 依据三份第七讲课件整理：**Oracle 册**《数据库安全 Oracle 安全概述》（42 页）、**SQL Server 册**《数据库安全 SQL Server 数据库安全》（71 页）、**注入册**《数据库安全 SQL 注入原理》（65 页）。`[Oracle 23]` 等表示原 PPT 页码。本讲把课件中的历史版本命令与通用安全原理分开标注。

## 一、本讲考点地图

1. **数据库安全目标与 Oracle 架构**：客户端—服务器、例程与数据库、文件/连接/资源风险；用户管理、备份恢复、资源管理。[Oracle 3–18]
2. **Oracle 授权**：DBA/开发者/普通用户，系统权限与对象权限，`GRANT`/`REVOKE`、角色、概要文件和资源限制。[Oracle 19–32]
3. **SQL Server 认证与访问控制**：Windows/混合身份验证、登录名与数据库用户、服务器/数据库/对象三级权限、固定角色与角色成员管理。[SQL Server 4–31]
4. **SQL Server 备份恢复与加密**：完整、差异、日志、文件备份；恢复顺序；服务器主密钥、数据库主密钥、证书和对称密钥。[SQL Server 33–68]
5. **SQL 注入**：输入变成 SQL 代码的根因、登录绕过的布尔逻辑、攻击类型与数据流、参数化查询及分层防护。[注入 3–63]
6. **全部课堂选择题与作业**：Oracle 册第 33–40 页；SQL Server 册第 70 页；注入册的登录示例和防范讨论。[Oracle 33–40；SQL Server 70；注入 15–20、26、57–63]

## 二、数据库安全的整体框架

数据库同时面临**未授权访问、越权修改、文件损坏、资源滥用、故障与数据泄露**。可按四个问题梳理措施：[Oracle 11–15]

| 问题 | 核心机制 | 对应目标 |
|---|---|---|
| 谁能连接？ | 账户与身份认证 | 排除未经授权者 |
| 连接后能做什么？ | 权限、角色、最小权限 | 机密性与完整性 |
| 操作是否可追踪？ | 审计/日志 | 可追责性 |
| 损坏后能否恢复？ | 备份、日志、恢复、闪回 | 可用性与完整性 |

资源限制用于防止少数会话耗尽连接、CPU、读取量等资源；加密保护数据与密钥，但**不能替代权限控制**。SQL 注入则跨越 Web 应用和数据库边界：数据库可能是在执行应用账号“合法持有”的权限，因此还要修正应用构造 SQL 的方式。[Oracle 15、28–32；SQL Server 53–55；注入 12–20]

## 三、Oracle：体系结构与安全入口

### 1. 例程、数据库、连接与文件

Oracle 服务端可概括为**例程（instance）+ 数据库（database）**。例程由内存结构（如 SGA）和后台进程组成，可启动/关闭；数据库包含数据文件、控制文件、重做日志等持久文件。客户端经连接/会话与例程交互，服务器进程处理 SQL 请求。[Oracle 8–12]

课件体系图还出现：

- **SGA**：共享池、数据高速缓存、重做日志缓冲区等共享内存区域。
- **PGA**：与服务进程处理请求有关的私有工作区。
- **DBWR、LGWR、CKPT、SMON、PMON** 等后台进程：分别参与数据写入、日志写入、检查点、恢复/监视等工作。考试若只问安全架构，记住**例程负责运行/处理，数据库文件负责持久保存**即可。[Oracle 9–10]
- **口令文件、参数文件、控制文件、数据文件、重做日志、归档日志**都在安全分析范围内。登录凭证泄露、文件被窃/损坏、资源滥用分别需要身份管理、存储保护与备份、资源限制应对。[Oracle 11–13]

连接与会话不是一个词：连接建立通信通道，会话承载已认证用户在数据库中的工作。提交用户名/密码、目标服务名等信息后，只有通过认证与授权，才能执行相应 SQL；会话中的后续操作仍要按权限检查。[Oracle 12]

### 2. 备份、导入导出与闪回

Oracle 课件强调**备份数据文件 + 归档/重做日志**用于把数据库恢复到合适时刻；`EXP/IMP`、`EXPDP/IMPDP` 是对象与数据的导出/导入工具；**闪回**用于在条件允许时恢复误操作的数据状态。[Oracle 15–18] 三者不能简单等同：导出文件、数据库备份、日志链和闪回的覆盖范围与恢复能力不同。答题先说明故障类型、恢复目标、可用备份/日志，再选方案。

## 四、Oracle：用户、权限、角色与概要文件

### 1. 用户类别和两种权限

**DBA**负责安装配置、账户与权限、安全管理、监控、备份恢复；**数据库开发者**设计数据结构与应用逻辑；**普通用户**做日常业务。不同岗位分配不同权限，是最小权限原则。[Oracle 19–21]

- **系统权限**：在系统范围执行操作，例如 `CREATE SESSION`（建立登录会话）、`CREATE TABLE`（创建表）。
- **对象权限**：在指定对象上执行操作，例如对 `Employees` 表 `SELECT`、`INSERT`、`UPDATE`、`DELETE`。[Oracle 22–23]

示例：[Oracle 23、39–40]

```sql
GRANT CREATE SESSION TO Martin;              -- 系统权限：允许建立会话
GRANT SELECT ON Employees TO John;            -- 对象权限：允许查询指定表
REVOKE SELECT ON Employees FROM John;         -- 撤回先前授予的对象权限
```

`GRANT` 是**DCL（数据控制语言）**；`REVOKE` 撤销授权。勿与 `CREATE` 一类 DDL、`INSERT/UPDATE` 一类 DML 混淆。[Oracle 37–40] 课件的 `CONNECT`、`RESOURCE`、`DBA` 是角色示例，角色是一组权限的封装；`GRANT CONNECT, RESOURCE TO MARTIN` 表示授予角色，**不是**把 `CONNECT/RESOURCE` 当成两个表权限。[Oracle 23–27] 角色和默认权限取决于版本/配置，答课件题按其示例，实际授权优先按所需具体权限与版本核对。

**创建角色**需要相应系统权限；课件以 `CREATE ROLE STUDENT`、`ALTER ROLE`、`DROP ROLE` 示意角色生命周期。[Oracle 27] “将对象权限、系统权限、角色放在同一个 `GRANT`”的语法受类别约束，课件第 26 页特别提醒对象权限不能与角色放在同一句授予；按对象权限单独写 `GRANT ... ON 对象 TO 用户/角色` 最清楚。[Oracle 26]

### 2. PROFILE：限制资源与口令

**概要文件 PROFILE**是分配给用户的一组资源/口令策略；默认概要文件与自定义概要文件均可用于管理会话数、CPU、连接/空闲时间、逻辑读等。[Oracle 28–32]

| 参数 | 约束对象 |
|---|---|
| `SESSIONS_PER_USER` | 单用户并发会话数 |
| `CPU_PER_SESSION` / `CPU_PER_CALL` | 每会话 / 每次调用 CPU 用量 |
| `LOGICAL_READS_PER_SESSION` / `..._PER_CALL` | 每会话 / 每次调用逻辑读块数 |
| `CONNECT_TIME` / `IDLE_TIME` | 最长连接时间 / 连续空闲时间 |
| `COMPOSITE_LIMIT` | 加权组合资源限制 |
| `PRIVATE_SGA` | 共享服务器模式下相关私有空间限制 |

[Oracle 30–31] **`RESOURCE_LIMIT` 管资源限制是否执行，不应推导为“关掉它就不执行密码策略”**；Oracle 文档明确说明 PROFILE 中的密码参数不受 `RESOURCE_LIMIT` 开关影响：[Oracle 资源限制说明](https://docs.oracle.com/en/database/oracle/oracle-database/19/dbseg/configuring-user-resource-limits.html)。课件第 32 页写 `ALTER SYSTEM SET RESOURCE_LIMIT=TRUE`，其考试意义是启用相应资源限制，不能概括为“所有 PROFILE 内容才生效”。

## 五、SQL Server：认证、三级权限与角色

### 1. 身份认证模式

- **Windows 身份验证模式**：由 Windows 身份体系认证，SQL Server 接受相应 Windows 身份；便于集中管理账户与安全策略。
- **混合模式**：同时接受 Windows 身份和 SQL Server 自身的登录名/密码。[SQL Server 4–7、70]

**登录名（login）**使主体能连接 SQL Server 实例；进入特定数据库并操作，还需对应的**数据库用户（user）**与权限映射。能登录实例不等于能读任何数据库。[SQL Server 8–12、19] `sa`、`sysadmin` 权限很高，遵循最小权限。课件关于默认 `BUILTIN\Administrators` 的描述针对旧版演示，勿当成现代系统的统一默认设置。[SQL Server 9]

### 2. 三层权限与固定角色

课件以**服务器级—数据库级—对象级**分权限：[SQL Server 11–12、19–21]

| 层级 | 例子 | 典型角色/对象 |
|---|---|---|
| 服务器级 | 管理登录名、创建数据库、配置实例 | `sysadmin`、`securityadmin`、`dbcreator` 等固定服务器角色 |
| 数据库级 | 管理库内对象、用户、备份 | `db_owner`、`db_backupoperator`、`db_ddladmin` 等 |
| 对象级 | 对具体表/视图 `SELECT`、`INSERT`、`UPDATE`、`DELETE`；执行存储过程 | 对象权限或列权限 |

还需认识 `db_datareader`（读库内用户表）、`db_datawriter`（修改库内用户表）、`db_denydatareader/db_denydatawriter`（拒绝对应操作）、`db_securityadmin`（库内权限管理）、`public`（所有数据库用户所属）。**角色权力范围越大越要谨慎授予**；不能把“数据库用户”与“服务器登录名”混同。[SQL Server 14、20]

课件用 `sp_addsrvrolemember/sp_dropsrvrolemember`、`sp_addrole/sp_droprole`、`sp_addrolemember/sp_droprolemember` 演示增删角色或成员。[SQL Server 17–18、28–31] 理解动作及服务器/数据库作用域即可。微软已将前两类角色成员旧过程标为弃用，新实现改用 `ALTER SERVER ROLE ... ADD/DROP MEMBER` 或 `ALTER ROLE ... ADD/DROP MEMBER`：[服务器角色文档](https://learn.microsoft.com/en-us/sql/t-sql/statements/alter-server-role-transact-sql)、[数据库角色文档](https://learn.microsoft.com/en-us/sql/relational-databases/security/authentication-access/database-level-roles)。

### 3. 用 SQL 实施自主访问控制

课件给出的通用授权与回收形式：[SQL Server 23–24、70]

```sql
GRANT SELECT, UPDATE (Sno) ON S TO U4 WITH GRANT OPTION;
REVOKE SELECT, UPDATE (Sno) ON S FROM U4;
```

第一句允许 U4 查询 S 表及修改其 `Sno` 列，且有权转授；第二句撤回。**有无 `WITH GRANT OPTION`**决定该授权是否附带转授权。课件第 24 页展示 `CASCADE/RESTRICT` 来说明级联撤销的**概念**；这属于教材式通用 SQL 表述，不能直接断言所示整句语法可在任意 SQL Server 版本执行。SQL Server 中还需区分 `GRANT`（授予）、`DENY`（显式拒绝）、`REVOKE`（撤掉原授予/拒绝，回到其他授权链的判定）。[SQL Server 23–24、69]

## 六、SQL Server：备份、恢复与加密

### 1. 备份类型、内容与恢复顺序

备份规划先问：备份哪些数据库/日志、谁有权备份、备份去哪里、多久一次、能接受多少数据损失与恢复时间。[SQL Server 33–39] 系统库示例：`master` 保存实例配置等关键元数据，`msdb` 保存作业/备份相关历史，`model` 是新数据库模板；用户数据库及事务日志也要纳入计划。[SQL Server 34]

| 备份类型 | 作用 | 恢复时注意 |
|---|---|---|
| 完整备份 Full | 保存某时刻数据库整体基线 | 先恢复基线 |
| 差异备份 Differential | 保存相对其**基础完整备份**以来发生变化的数据 | 先有对应完整备份，再恢复选定差异备份 |
| 事务日志备份 Log | 保存日志链中一段连续记录 | 满足适用恢复模式；按时间顺序恢复所需日志 |
| 文件/文件组备份 | 仅备份指定数据文件/文件组 | 需要与恢复策略和日志链配合 |

[SQL Server 40–49] **恢复顺序示例**：先恢复完整备份 → 如有适用的差异备份则恢复最新差异备份 → 依次应用差异之后所需的日志备份 → 最后恢复数据库可用状态。应用中间备份时不要提前结束恢复链；日志备份是否可用与数据库恢复模式有关。[微软日志恢复文档](https://learn.microsoft.com/en-us/sql/relational-databases/backup-restore/apply-transaction-log-backups-sql-server) 课件常考“差异备份不能脱离基础完整备份”“日志须按链恢复”。[SQL Server 41–42、49–51]

识别命令即可：[SQL Server 45–51]

```sql
BACKUP DATABASE StudentCourse TO backup_device;                    -- 完整
BACKUP DATABASE StudentCourse TO backup_device WITH DIFFERENTIAL;  -- 差异
BACKUP LOG StudentCourse TO log_backup_device;                     -- 日志
RESTORE DATABASE StudentCourse FROM backup_device;                -- 恢复起点示意
```

课件的 `INIT/NOINIT` 涉及备份介质覆盖/追加，操作前必须确认目标；这些是课堂语法示意，不构成一套可直接用于生产恢复的完整脚本。[SQL Server 45–51] **备份成功不等于可恢复**：还须保护备份访问、保存密钥/证书、核对恢复链并定期验证恢复能力。

### 2. 加密层次与密钥保护

SQL Server 课件以 2005 版本介绍对称密钥、非对称密钥和证书，并给出层次：**服务主密钥（SMK）→ 数据库主密钥（DMK）→ 证书/非对称密钥 → 对称密钥 → 数据**。上层密钥用于保护下层密钥；真正使用时还要保证密钥备份和访问限制。[SQL Server 53–55]

- `BACKUP SERVICE MASTER KEY` / `RESTORE SERVICE MASTER KEY`：备份、恢复服务主密钥。[SQL Server 56–58]
- `CREATE MASTER KEY`、`BACKUP MASTER KEY`、`RESTORE MASTER KEY`：数据库主密钥生命周期。[SQL Server 59–61]
- `CREATE CERTIFICATE`、`Cert_ID`、`EncryptByCert`、`DecryptByCert`：课件的证书标识与加解密示例。[SQL Server 62–68]

不要照抄课件中的 `123456` 之类演示密码，也不要把证书加密当成访问授权或备份恢复的替代物。加密数据和**能否访问明文**取决于密钥管理、数据库权限与应用逻辑共同控制。[SQL Server 55–68]

## 七、SQL 注入：原理、类型与防范

### 1. 根因：把数据拼成了代码

典型 Web 系统由浏览器、应用服务器与数据库组成。应用服务器接收表单、URL 或 Cookie 输入后生成 SQL，再交数据库执行。[注入 3–12、56] **SQL 注入**的根因是应用把不可信输入直接拼进 SQL 文本，使输入有机会改变原查询的语法与逻辑。[注入 12、20]

课件登录例将用户名与口令拼入：

```sql
SELECT id FROM users
WHERE username = '输入的用户名' AND password = '输入的口令';
```

若用户名输入包含结束字符串、布尔恒真条件与注释标记，拼接后的 SQL 可能把原口令条件注释掉或让条件恒真，查询返回本不应返回的用户记录。[注入 15–20] **`OR 1=1` 是否真能绕过取决于括号、`AND/OR` 优先级、注释位置以及程序如何处理返回结果**；例如仅插入 `OR '1'='1` 而保留后续 `AND password=...`，并不能仅凭字符串就断言“必定登录成功”。考试按课件第 16–19 页完整拼接过程分析，不死背一个片段。[注入 16–19、47–49]

攻击后果可以是越权读取、修改或删除数据；若数据库账号还具有危险系统权限，损害会扩大。课件第 25 页按“识别环境→确定数据库/表结构→读取目标数据”讲攻击路径，学习重点是**每一步所依赖的信息暴露与权限失守**，不是实际操作目标站点。[注入 21–25]

### 2. 课件列出的注入形态

| 类型 | 利用什么反馈或入口 | 需要记住的判别点 |
|---|---|---|
| 布尔/登录绕过 | WHERE 条件被改写 | 查询真假或返回行数改变 |
| `UNION` 注入 | 合并另一个查询的结果 | 查询列数、类型必须兼容 |
| 报错型 | 数据库错误回显 | 错误文本泄漏结构/版本等信息 |
| 盲注：布尔型/时间型 | 不直接回显数据，观察响应差异/延迟 | 一次推测少量信息 |
| 堆叠查询 | 接口/驱动允许多语句执行 | 可能追加其他 SQL 操作，取决于配置 |
| 存储过程注入 | 过程内部再拼接动态 SQL | “调用存储过程”本身不保证安全 |
| Cookie/URL/表单入口 | 不可信数据的来源不同 | 服务端必须统一处理，不能只验证可见输入框 |

[注入 27–56] 课件第 50 页 `UNION` 示例把原查询的**两列**与追加查询的**三列**合并，按通常 SQL 规则不能直接运行；答考点时写“列数及可转换类型必须匹配”。第 53–55 页又把不同数据库方言/功能（如时间函数和系统命令过程）放在一组例子中，**不可认为所有数据库或默认配置都支持**。课件第 28 页称防火墙不会发现 SQL 注入也过于绝对；网络控制或检测可补充，但不能替代修复应用层拼接漏洞。

### 3. 最重要的防线：参数化

**参数化查询**先固定 SQL 结构，再把用户输入绑定为参数值；参数不会被重新解释成 SQL 关键字或查询结构。课件的 Java/JDBC 示例：[注入 57–60]

```java
String sql = "SELECT id FROM users WHERE username=? AND password=?";
PreparedStatement ps = connection.prepareStatement(sql);
ps.setString(1, username);
ps.setString(2, password);
```

这段演示的是**如何绑定输入**；真实登录系统不应把用户密码明文直接放在数据库列中比较，应采用合适的密码验证方案。`PreparedStatement` 的安全性来自**绑定数据与 SQL 结构分离**，不是“预编译一定让每次查询更快”。若先把用户输入拼入 SQL 再 `prepare`，依然有注入风险。[注入 57–61；OWASP SQL 注入防护指南](https://cheatsheetseries.owasp.org/cheatsheets/SQL_Injection_Prevention_Cheat_Sheet)。

防护层次：[注入 36–38、57–63]

1. **参数化所有外部值**：表单、URL、Cookie、请求头、后台任务与存储过程参数一视同仁。
2. **无法参数化的 SQL 结构**（表名、列名、排序方向）使用应用内部固定的**允许列表**映射，不让外部值直接成为结构。
3. **按业务验证输入**：类型、长度、范围、格式；但“删掉单引号”“仅过滤危险词”不能替代参数化。
4. **数据库最小权限**：应用连接账号只获必要的表/操作权限，避免高权限账号扩大损害。
5. **减少错误回显，审计与更新**：避免向客户端暴露数据库内部错误，监控异常请求并及时修补。

“过滤单引号”“不规则加密用户名密码”等是课件旧案例的应急思路，[注入 36–46] **不能当作可靠的根本防线**；优先使用参数化和允许列表。[OWASP SQL 注入防护指南](https://cheatsheetseries.owasp.org/cheatsheets/SQL_Injection_Prevention_Cheat_Sheet) 另外，**SQL 注入与 XSS 不同**：前者是输入改变数据库命令，后者是恶意脚本在浏览器执行；XSS 题目答输入验证时还应考虑输出时按上下文编码。[Oracle 33]

## 八、课堂练习、选择题与作业答案

### 1. Oracle 册第 33–40 页（全部选择题）

|---|---|---|---|
| 33 | 防止 XSS | **D：对用户输入过滤和验证** | 四项中最接近；实际防 XSS 还要对输出做上下文编码，数据库备份不能防 XSS |

### 2. SQL Server 册第 70 页作业

1. **身份认证模式有哪些？** Windows 身份验证模式；混合模式（Windows 身份 + SQL Server 登录身份）。连接实例的登录名与具体数据库用户需区分。[SQL Server 4–10、70]
2. **如何用 SQL 实施自主访问控制？** DBA/有授权权力的主体按客体与操作授予 `GRANT 权限 ON 对象 TO 主体`，必要时给转授权；再用 `REVOKE` 收回。可通过角色集中分配，按服务器、数据库、对象作用域检查有效权限；显式拒绝要另看 `DENY`。[SQL Server 11–31、70]
3. **如何备份和恢复数据库？** 明确备份范围/频率/介质与授权 → 建立完整备份基线 → 按恢复目标安排差异和日志备份 → 恢复时先完整、后对应差异、再按顺序应用日志 → 验证可用性及数据一致性，并保护备份与密钥。[SQL Server 33–51、70]

### 3. 注入册课堂讨论

1. **为什么不知道合法用户名/口令仍可能登录？** 因为程序拼接 SQL，攻击输入改变 `WHERE` 布尔表达式或截断原口令条件；数据库返回了非授权记录，应用又把“有记录”误判为成功。[注入 15–20]
2. **SQL 注入从哪里进入？** 不只登录表单，也可能是 URL 参数、Cookie、后台传入的任何不可信值；是否可注入取决于服务端怎样构造 SQL。[注入 27–56]
3. **怎样修复？** 把动态值改为参数绑定；结构性名称用允许列表；按业务验证；给应用账号最小权限；保护错误与审计信息。仅转义几个字符或只靠防火墙不足以根治。[注入 36–38、57–63]

## 九、考前自测

1. 分别举出 Oracle **系统权限**与**对象权限**的例子；`GRANT SELECT ON T TO U` 属哪类？
2. SQL Server 某主体能登录实例却不能查询 `Sales.Orders`，可能缺哪两层映射或授权？
3. 有完整备份 F、基于 F 的差异备份 D，以及 D 之后的日志备份 L1/L2。要恢复至 L2 结束，写出顺序。
4. 为什么用 `PreparedStatement` 前先拼接用户名仍不能防 SQL 注入？排序列名为何不能直接用 `?` 占位？
5. 说明“数据库备份”“加密”“审计”分别解决什么问题，哪一个能直接防止 SQL 注入？
6. Oracle `RESOURCE_LIMIT=FALSE` 时，PROFILE 的密码策略是否都失效？

**答案**：1. `CREATE SESSION` 是系统权限；`SELECT ON T` 是对象权限。2. 可能未映射目标数据库用户，或未授予该对象 `SELECT`/相应角色权限。3. F → D → L1 → L2，日志按连续链顺序恢复。4. 拼接时输入已变成 SQL 结构；参数占位符绑定的是值，表/列名等结构需允许列表映射。5. 备份处理恢复，加密处理数据保密，审计处理追踪；三者均不能直接修复应用拼接，需参数化。6. 不会；资源限制的开关与密码参数的实施不是同一件事。

## 十、最后记忆卡与课件辨析

- **Oracle**：例程 = 内存 + 进程；数据库 = 持久文件；安全三板块 = 用户管理、资源管理、备份恢复。权限分系统/对象；角色汇集权限；PROFILE 管资源与口令。[Oracle 9–32]
- **SQL Server**：Windows/混合两种认证；登录名 ≠ 数据库用户；服务器级/数据库级/对象级三层权限。`GRANT` 授予、`DENY` 拒绝、`REVOKE` 撤回。[SQL Server 4–31]
- **备份恢复**：完整是基线，差异依赖对应完整备份，日志沿链按顺序应用。密钥分层保护，密钥丢失会影响解密数据。[SQL Server 33–68]
- **SQL 注入**：根因是输入被拼进 SQL 代码；按类型识别结果回显、错误、布尔/时间侧信道与不同输入来源；**参数化查询 + 结构允许列表 + 最小权限**是答题主线。[注入 12–63]
- **易错课件示例**：Oracle 第 5 页“21c 是最新版本”是特定时期陈述，不作为固定考点；SQL Server 册以 2005 为例，旧角色存储过程已弃用；注入册的若干 SQL 片段有列数、运算优先级或方言前提，考试要从实际查询结构推导结果，不把示意文本当成各数据库通用可执行语句。[Oracle 5；SQL Server 17–31；注入 47–55]
