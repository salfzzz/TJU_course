## 二、操作系统安全的定位

操作系统直接管理硬件资源，提供用户和应用运行的平台；因此账户、文件、进程、设备与系统服务的安全都依赖其机制。[概论 8–9] 课件以 Windows XP 停止支持为背景说明：长期缺少维护会增加安全风险。这是**历史案例**，考点是“维护和更新的重要性”，不必记成当前服务状态。[概论 5–7]

**保护内容**分两层：[概论 11–12]

- **用户与资源安全**：身份鉴别、授权访问控制、数据保密与完整性保护。
- **系统自身安全**：抗攻击、系统文件及核心组件完整性、故障或入侵后的可信恢复。

**四类安全需求**：[概论 14–16]

| 需求 | 要解决的问题 | 典型机制 |
|---|---|---|
| 机密性 Confidentiality | 非授权主体不能得知秘密数据 | 权限、加密、隔离 |
| 完整性 Integrity | 非授权或不合规则的修改不能破坏正确状态 | 访问控制、校验、良构操作 |
| 可用性 Availability | 合法用户需要时能够获得服务 | 容错、恢复、资源保护 |
| 可记账性/可审计性 Accountability | 能把安全事件与责任主体关联并核查 | 标识、日志、审计 |

电子交易例还要求双方身份可确定、信息不被伪造、交易不可抵赖、交易数据完整。[概论 15] “审计”是形成可记账性的手段之一，**有日志不等于自动获得不可抵赖性**；日志还要可追溯、受保护并与可靠身份绑定。[概论 14 注、16、38]

## 三、安全策略、TCB 与 TCSEC

**安全需求**说“想获得什么保障”，**安全策略**说“采用什么授权和保护规则”，**安全机制/实现**负责实际执行规则。策略按课件分为**访问控制策略**和**访问支持策略**：前者规定主体能怎样访问客体，包括 DAC、MAC、RBAC；后者保证这些规则得到可靠执行。[概论 17–25、33]

RBAC 在银行的课堂例子：[概论 27–28]

- 出纳员可处理规定范围内的账户操作；分行管理者还可创建、终止账户。
- 顾客只查询**自己的**账户；系统管理员管理系统但不应因此获得客户账户数据的读写权。
- 审计员可读取审计所需数据，却不修改业务数据。

答题时把角色写成“**权限赋予角色，用户被指派角色**”，并体现最小权限和职责分离。RBAC 详细模型见第五讲讲义。[概论 25–28]

### 1. 可信计算基 TCB

**TCB**（Trusted Computing Base）是负责实施安全策略的硬件、固件与可信软件的组合，不仅仅是一组软件，也不是一种网络协议或密码算法。[概论 29–31] 其软件核心承担安全运行、标识用户、可信登录路径、主体对客体的访问控制、监视和审计等任务。[概论 30]

TCB 应成为可信的保护基础：如果执行访问检查的核心组件本身可被绕过或篡改，外层规则再严也不可靠。评价时关注它是否满足机密性、完整性、可用性等安全目标。[概论 29–32]

### 2. TCSEC 及访问支持要求

**TCSEC**（“橙皮书”）是课件介绍的历史评估标准。课件按 `D < C < B < A` 概述等级：D 为最低，C 强调自主访问控制，B 包含更强的强制访问控制，A 为更高保证等级；等级内还有子级。[概论 34] 这是标准知识点，**不能把某个现代 Windows/Linux 产品直接按这四档推断等级**。

课件列出的六类访问支持要求：[概论 36–41]

1. **标识与鉴别**：唯一标明用户并核实其身份；可用“知道的、持有的、生物特征”等因素。[概论 37]
2. **可审计性**：记录并保护影响安全的事件，关联到可辨认的主体。[概论 38]
3. **客体重用**：存储页、磁盘块等资源重新分配前，不让新主体看到上个使用者残留信息。[概论 39]
4. **确切保证**：有证据表明安全机制按策略正确实现、运行。[概论 40]
5. **连续保护**：保护机制在运行过程中持续防篡改、防绕过。[概论 40]
6. **隐蔽信道分析**：识别非预期的信息传输途径，如利用共享资源状态传递秘密。[概论 41]

区分：**普通通信信道**是设计用于传输信息的接口；**隐蔽信道**借未设计为通信接口的状态或资源传递信息。访问控制规则本身可能挡不住它。[概论 41]

## 四、Windows：标识、鉴别与口令保护

Windows 安全流程可记为：**标识 → 鉴别 → 授权/访问检查 → 审计**。[概论 43；Windows 3–4]

### 1. 本地账户、域账户、SAM 与 SID

- **本地账户**在本机管理和验证；**域账户**由域服务集中管理。课件把域与工作组对比，重点是集中身份与策略管理。[概论 44–48]
- **SAM**（Security Account Manager）是本地账户数据库，课件给出 `C:\Windows\System32\config\SAM` 路径；运行中的文件受保护，脱机取得存储内容仍构成风险。[概论 48；Windows 5–14]
- **SID**（Security Identifier）是安全主体的标识符，用户与组各有 SID；主体的显示名称可以改变，访问检查主要识别 SID。课件中的长串 `S-1-...-RID` 是示例，末段为 RID，勿把 SID 当成固定“48 位字符串”。[概论 46；Windows 44–46]
- Windows XP 的 **GINA—Winlogon—LSA** 流程是课件的**旧版登录案例**；核心理解是登录组件收集凭证，安全子系统完成验证并建立后续访问所需的安全上下文。[概论 48–49]
- 课件罗列 SMB、LM、NTLM、Kerberos 等远程访问相关技术。[概论 50] **SMB 是文件共享协议，不等同于一种“明文口令认证协议”**；不要把表中“SMB：口令明文传输”当成普遍规律。LM/NTLM/Kerberos 的作用也应区分“存储哈希”与“网络认证协议”。

### 2. 密码攻击与防护

**字典攻击**试常见口令或字词组合；**暴力破解**遍历候选空间；**在线攻击**面对登录接口，受账户锁定和限速影响；**脱机攻击**拿到口令哈希后本地猜测，不再触发登录失败计数。[Windows 7–12] 因此 SAM 文件受保护、磁盘加密、强口令、登录失败策略都各有作用。

课件中的密码策略包括长度、复杂度、历史、防止重复使用；账户锁定策略包括锁定阈值、计数器复位时间、锁定时长。[Windows 9–10] “输错五次、锁定三十分钟”是示例配置，**不是所有 Windows 的固定默认值**。[Windows 10 注]

### 3. LM 哈希与 NT 哈希：必考对比

| 项目 | LM 哈希（旧兼容机制） | NT 哈希 |
|---|---|---|
| 大小写 | 先把字母转大写，丢失大小写差异 | 区分大小写 |
| 处理方式 | 口令按旧机制处理为 14 字节、拆成两段各 7 字节；两段分别作为 DES 密钥加密固定字符串，再拼接 | 将密码按 UTF-16LE 编码后做 MD4，形成 128 位摘要 |
| 长度与弱点 | 两段可分别猜解；短于 8 字节时第二段固定；旧机制不适合长密码 | 不存在 LM 的两段/大写弱点，但本身也不是加盐、慢速的现代密码存储方案 |
| 课件定位 | 用于解释历史弱口令设计 | 与 LM 对比，理解大小写、分段与算法差异 |

[Windows 14–32] **两种完整哈希值都是 128 位**：LM 由两个 64 位 DES 输出拼接；课件第 32 页把 LM 写成“64 bit”只对应一半输出，应修正。课件把“散列加密”混称，严格说**哈希是单向摘要，和可解密的加密不同**。课件第 25 页“超过 14 字节只取前 14 字节”也不宜当成所有情形的规则；传统 LM 机制对超过 14 字符的密码并不产生正常的 LM 哈希。微软文档亦说明 LM 哈希存储自 Windows Vista / Server 2008 起默认禁用：[微软密码技术概述](https://learn.microsoft.com/windows-server/security/kerberos/passwords-technical-overview)、[LM 哈希存储说明](https://learn.microsoft.com/en-us/troubleshoot/windows-server/windows-security/prevent-windows-store-lm-hash-password)。

**课堂讨论：LM 不安全在哪里？** 答：大写化损失大小写组合、分成独立短段、短口令第二段固定，且计算快，故猜测成本低。[Windows 23–26] 记住过程与原因，比死背演示哈希值重要。

**彩虹表**是用计算时间换存储空间的预计算查找技术，含哈希与约简函数构成的链；约简函数不是哈希的真正“逆函数”。链更长通常节省表空间但查询计算更多。课件第 35 页把彩虹表说成“预先计算好的哈希集合”是入门简化，第 36–38 页才展示哈希与约简、时空权衡。[Windows 33–38] 长而随机、唯一的口令会扩大猜测空间；加盐机制也能使同一口令的预计算表难以跨账户复用。**NT 哈希本身不加盐**，所以不能把其安全性理解成“有盐”。[微软密码技术概述](https://learn.microsoft.com/windows-server/security/kerberos/passwords-technical-overview)

**如何保护 SAM？** 限制本地/离线读取、保护系统与磁盘、减少高权限账户、提高口令质量并审计异常访问。[Windows 39–40] 课件提到 `syskey.exe`，这是**历史机制**；微软说明该工具已不受支持，并推荐 BitLocker 等技术保护启动期数据：[微软 Syskey 说明](https://learn.microsoft.com/en-us/troubleshoot/windows-server/active-directory/syskey-exe-utility-is-no-longer-supported)。考试可回答“课件以 Syskey、BitLocker 说明保护存储”，实际配置不能照着旧图找 Syskey。

## 五、Windows：访问令牌、DACL/SACL 与 ACE 判题

### 1. 五个组件和访问检查流程

| 组件 | 属于哪边 | 作用 |
|---|---|---|
| SID | 用户/组等安全主体 | 表示“是谁” |
| 访问令牌 Access Token | 进程/线程的访问上下文 | 含用户和组 SID、特权等，说明“请求者带着什么身份/能力” |
| 安全描述符 Security Descriptor | 受保护对象 | 含所有者及访问控制信息 |
| DACL / SACL | 对象安全描述符中的列表 | DACL 管允许/拒绝；SACL 管审计 |
| ACE | ACL 中的条目 | 将 SID、允许/拒绝/审计类型和访问掩码关联 |

[概论 51–56；Windows 42–50] 课件问“访问令牌是什么”时，答**用于表示访问主体安全上下文的数据结构**，不是密码；“安全描述符是什么”时，答**对象的访问控制与审计信息**，不是登录文件。令牌中的用户及组 SID 与 DACL 中 ACE 的 SID 匹配，结合请求的读、写等权限作出决定。[概论 52–58]

访问检查的简化步骤：[概论 56–61；Windows 54–59]

1. 明确请求的**全部权限**，例如只请求读，还是同时请求读和写。
2. 从令牌取用户 SID、相关组 SID；读取对象 DACL，按 ACE 的**实际顺序**检查。
3. 与令牌匹配的拒绝 ACE 若命中仍未满足的请求权限，拒绝；允许 ACE 可逐项满足请求权限。全部请求权限获准才允许；遍历完仍有未获准部分则隐式拒绝。
4. 常规排序是**显式 ACE 在继承 ACE 前；同一层显式拒绝在显式允许前；继承层级再按顺序处理**。顺序能影响结果，故“拒绝优先”是课件典型顺序下的速记，不应忽略实际 ACE 顺序。[Windows 54；微软 ACE 排序说明](https://learn.microsoft.com/en-us/windows/win32/secauthz/order-of-aces-in-a-dacl)

**无 DACL 与空 DACL 必须区分**：无 DACL / 空指针 DACL 时，普通 DACL 访问检查不限制访问；**存在但没有 ACE 的空 DACL**通常不授予权限。课件第 61 页第一问“安全描述符中不存在 DACL”应答**允许**，第二问“所有 ACE 的 SID 均不匹配”应答**拒绝**。[概论 56–61；微软访问检查说明](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-dtyp/4f1bbcbb-814a-4c70-a11e-2a5b8779a6f9) 实际系统还有所有者隐含权、特权等特殊规则，考试基础题先按给定 DACL 条件判断。

### 2. 课件两道权限合并题

- **用户 A 对文件有“允许读”，所属 Teachers 组有“允许写”**：令牌含用户与组 SID，两项允许权限可累加，所以 A **可读、可写**。[Windows 41、60]
- **用户 A 有“允许读写”，Teachers 组有“拒绝写”**：按题目默认的规范 ACE 顺序，拒绝写生效，A **可读、不可写**。[Windows 41、61] 若应用一次性请求“读 + 写”两种权限，**整个复合请求失败**；分别请求读则可成功。这里区分“有效权限”与“一次请求的结果”。

### 3. 审计及其他 Windows 保护

**SACL**指定哪些主体的哪些操作需要审计，事件查看器可查看系统、应用程序、安全等日志；先配置相应审核策略才会得到所需记录，并需保护日志免遭擅改。[概论 55、62–66；Windows 62–65] 课件给出的旧 `.Evt` 文件名和路径是**历史示例**，复习应掌握“审核策略—安全事件日志—事件查看器”的关系，不把旧路径当成当前通用路径。

**BitLocker**面向卷/磁盘加密，**EFS**是文件加密机制；**UAC**用于管理权限提升的交互控制；**Windows 防火墙**控制网络通信。这些机制分别处理静态数据、提权交互和网络流量，不能代替 DACL 对单个对象的授权判断。[Windows 4、66–70] 课件的管理共享与隐藏共享只需认识是网络共享管理问题；不要把“删除 `c$` 共享”背成通用安全策略。[Windows 69]

## 六、Linux：账户、权限与日志

### 1. 用户、组与认证

Linux 用 **UID** 表示用户、**GID** 表示组；文件有所有者及所属组，访问检查把进程身份与文件所有者、组及其他用户权限比较。`root` 是高权限账户，日常操作应控制其使用。[概论 70]

| 文件 | 核心内容 | 复习要点 |
|---|---|---|
| `/etc/passwd` | 用户账户条目、UID/GID、家目录、登录 shell 等 | 通常可供读取；其密码字段可能是指向 shadow 的占位符 |
| `/etc/shadow` | 密码验证信息及相关期限字段 | 访问受限；存的是口令哈希/验证材料，不是可直接读出的明文 |
| `/etc/group` | 组定义与成员关系 | 对应组信息 |
| `/etc/gshadow` | 受保护的组认证与管理信息 | 对应组的受限信息 |

[概论 70–72] 课堂作业是**比较 `/etc/passwd` 与 `/etc/shadow`**：可从字段、可读范围、口令信息保存位置、分离后的安全意义四方面答。PAM 是可插拔认证模块框架；课件还列本地登录、远程登录、基于证书的主机信任。[概论 71–72]

### 2. 权限位与数字模式

`ls -l` 的前三组三位依次表示**所有者 / 所属组 / 其他用户**；每组的 `r=4、w=2、x=1`，相加得到八进制数字。[概论 73–74]

```text
-rwxr-xr--  →  所有者 rwx=7；组 r-x=5；其他 r--=4  →  754
chmod 755 filename  →  所有者 rwx；组 r-x；其他 r-x
```

对**普通文件**，`r` 可读内容，`w` 可修改内容，`x` 可执行；对**目录**，`r` 可列目录项，`w` 可增删/更名目录项，`x` 可进入并按名称访问。目录实际操作常需多个权限配合。`chmod` 修改权限模式，`chown` 修改属主，两者不混淆。[概论 73–74、91–93]

### 3. 日志与基础措施

课件列出登录/连接日志（如 `wtmp`、`utmp`）、系统日志、应用程序日志，并以 `last` 查看登录历史为例。[概论 75] 具体文件位置因发行版及日志组件而异，考试按课件例子理解日志类别与作用即可。安全措施可包括及时更新、强口令、适当限制远程 root 登录、配置防火墙、审计；它们共同作用，不能只靠其中一个。[概论 76]

## 七、Symbian 与智能终端安全

Symbian 是课件用来讨论**移动操作系统安全设计**的历史案例，关注架构，不必死记旧市场数据。[概论 77–81]

- **分层信任**：底层可信计算基包括内核、文件服务器、安装程序；中间可信计算环境为重要服务提供受限资源访问；上层应用不能直接获得所有敏感资源，而经受信服务访问。[概论 82–83]
- **数据锁定/目录隔离**：课件例中 `/sys` 为系统目录、`/private` 隔离应用私有数据、`/resource` 给普通进程只读访问。考点是“按进程/目录控制读写和执行”，不要把这些路径套用到 Linux 文件系统。[概论 84]
- **应用安装认证**：敏感资源的使用结合安装包认证/签名；签名验证用于确认软件来源与完整性，降低篡改和重打包风险。[概论 85、94]
- **可信用户界面**：保护密码等敏感输入，不让别的进程轻易窥取屏幕与输入事件。[概论 86]
- **备份与恢复**：恢复可执行程序要考虑重新安装与认证，私有数据恢复还要维护应用边界。[概论 87]

概论册末尾的 Android 题虽正文主要讲 Symbian，考点是**应用签名和代码签名验证可帮助识别重打包**。[概论 94]

## 八、课件练习题与讨论题答案

### A. 操作系统概论册

1. **[31] 什么是 TCB？** 选 **B**：共同执行安全策略的硬件与软件组件；完整定义还包含固件与可信软件。[概论 29–31]
2. **[32] TCB 的安全性评估包括哪些方面？** 选 **D**：机密性、完整性、可用性。题目问安全性目标，不是一般工程性能。[概论 32]
3. **[61] 无 DACL / ACE SID 全不匹配？** 前者在基本 DACL 检查中**允许**；后者**拒绝**。特别区分“无 DACL”与“空 DACL”。[概论 56–61]
4. **[68] Windows 登录安全最佳实践？** 题目四项中选 **C：定期更改密码**；弱密码、禁用自动锁定、共享账户均不合适。此题在给定选项内成立，**不应推出“所有账号必须固定周期强制改密”**。更关键的是强而唯一的密码、避免泄露和恰当的锁定/认证保护。[概论 68]
5. **[71] 作业：查看 `/etc/passwd` 与 `/etc/shadow`。** 答题框架见第六节，重点为用户基本资料与受保护密码验证信息的分离。[概论 71]
6. **[76] 提高 Linux 安全性的“最重要”措施？** 选项 A 防火墙、B 定期更新、C 禁用 root 登录、D 强密码。若课堂必须单选，通常按**B：定期更新操作系统**作答；但题干没有限定威胁模型，四项均有价值，“最重要”并无普遍唯一答案。[概论 76]
7. **[88] 访问令牌？** 选 **B**：用于访问控制的安全上下文数据结构。[概论 52、88]
8. **[89] 安全描述符的用途？** 选 **C**：描述对象的访问控制与相关审计信息。[概论 54、89]
9. **[90] DACL 的 ACE 通过什么标识主体？** 选 **B：SID**。[概论 55–57、90]
10. **[91] Linux 权限数字所表示的三种权限？** 选 **D：读、写、执行**；选项 B 的英文“Run”虽近义，但题目标准术语是 `Read/Write/Execute`。[概论 74、91]
11. **[92] `-rwxr-xr--` 谁能写？** 选 **A：文件所有者**。[概论 74、92]
12. **[93] 修改文件/目录权限的命令？** 选 **A：chmod**。[概论 74、93]
13. **[94] 如何帮助防止 Android 应用重打包？** 选 **D：应用签名和代码签名验证**。验证可发现签名不符；仍要配合可信分发与完整性检查。[概论 94]

### B. Windows 册

14. **[7–8] 口令认证有哪些安全威胁？** 字典猜测、暴力猜测、脱机哈希猜测；口令复用和凭证被窃也会增加风险。在线限速/锁定与脱机哈希保护的防护对象不同。[Windows 7–12]
15. **[11] 如何发生脱机口令猜测？** 课件情景是攻击者在脱机环境得到 SAM 中的验证材料后本地测试候选口令。防护要点是保护设备与存储、限制高权限访问、磁盘加密、强口令，而非只设置在线锁定阈值。[Windows 11–13]
16. **[23] LM 哈希有哪些弱点？** 大写化、7 字节分段、短口令第二段固定；见第四节。[Windows 23–26]
17. **[33] 如何提高猜测效率？** 课件引出预计算彩虹表及其时间/空间权衡；答题强调减少重复计算，同时说明强随机口令和适当保护能增大攻击成本。[Windows 33–38]
18. **[39] 如何保护 SAM？** 见第四节末；Syskey 只作为旧版本课件材料。[Windows 39–40]
19. **[41、60] 用户允许读 + 组允许写？** 有效权限为读写。[Windows 60]
20. **[41、61] 用户允许读写 + 组拒绝写？** 按常规 ACE 顺序，有效权限仅读；读写合并请求整体失败。[Windows 61]

## 九、考前自测

1. 写出“安全需求—安全策略—TCB—审计”的关系；为什么日志必须受保护？
2. 线程带用户 SID `U`、组 SID `G`，请求 `R+W`；DACL 顺序为“拒绝 G 的 W、允许 U 的 R+W”。本次请求是否成功？改为只请求 R 呢？
3. 为什么“空 DACL”和“没有 DACL”结果相反？
4. 将 `-rw-r-----` 写成数字权限；若要给所属组加执行权，修改后是多少？
5. 用一句话分别解释 SID、Access Token、Security Descriptor、DACL、SACL。
6. LM 哈希为什么会使短于 8 字节的口令更容易暴露长度线索？

**自测答案**：1. 需求定义目标，策略定义规则，TCB 执行策略，审计记录执行过程；日志若可被改写便无法可靠追溯。2. `R+W` 被拒；只请求 R 可由允许 ACE 满足。3. 没有 DACL 表示没有该访问列表限制；存在但无允许 ACE 则未取得所请求权。4. `640`；所属组加执行权后 `650`。5. SID 标识主体；令牌描述请求者安全上下文；安全描述符描述对象安全属性；DACL 决定访问；SACL 决定审计。6. 第二个 7 字节分段全为填充值，其 DES 输出固定。

## 十、课件表述辨析与最后记忆卡

**需辨析的旧版或简化表述**：

- `GINA`、`syskey.exe`、`.Evt` 路径和 Windows XP 认证图是历史案例；复习其安全原理，不照图配置现代系统。[概论 49、66；Windows 39–40、65]
- Windows 册第 32 页将 **LM 完整哈希写成 64 bit**，应是两个 64 位部分拼成 **128 bit**；第 45 页将 SID 写成固定“48 位字符串”，也不应照背。[Windows 21–22、32、45]
- 哈希与加密不同；**NT 哈希**是存储/验证用的摘要，**NTLM**是相关身份认证协议族，二者不能当同一个概念。[概论 50；Windows 28–32]
- “拒绝优先”应结合 ACE 的**顺序**和**请求的具体权限**判断；“无 DACL”与“空 DACL”相反。[概论 56–61；Windows 54–61]
- Linux 第 76 页与 Windows 第 68 页的“最佳/最重要”只在课堂给出的选项和语境下回答，实际安全措施需组合使用。[概论 68、76]

**一分钟记忆**：

> 需求是“机密、完整、可用、可追责”；策略分“控制访问”和“支持控制”；TCB 负责可信执行。Windows 看令牌与安全描述符，DACL 判允许/拒绝，SACL 判审计；用户和组的允许权可累加，命中的拒绝权需按 ACE 顺序判断。Linux 看 UID/GID、`rwx` 与 `4/2/1`。移动系统看分层信任、数据隔离、签名与可信输入。
